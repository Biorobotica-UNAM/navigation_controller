# navigation_controller

This repository implements a custom ROS navigation controller module based on
the [pumas_nav2](https://github.com/ARTenshi/pumas_nav2) package for
Bio-Robotics Lab robots.

## `nav_controller_node`

`nav_controller_node` is the bridge between semantic executor requests and the
navigation stack.

It exposes:

```text
/nav_controller/go_to_location
```

using:

```text
known_locations_interfaces/srv/LocationsGet
```

Request:

```text
string location_name
```

Response:

```text
bool success
string message
geometry_msgs/Pose pose
```

## Flow

1. Receive a semantic location name, for example `kitchen`.
2. Query `locations_manager/get` to resolve that name to a map pose.
3. Publish the resolved `PoseStamped` goal on `nav_control/goal`.
4. Wait for navigation status on `navigation/status`.
5. Return success or failure with the status text preserved in `message`.

## Terminal Status Handling

The controller treats these `actionlib_msgs/msg/GoalStatus` values as terminal:

```text
SUCCEEDED
PREEMPTED
ABORTED
REJECTED
RECALLED
LOST
```

Only `SUCCEEDED` returns `success = true`. The other terminal states return
`success = false`.

The original planner status text is preserved. This is important because the
executor and supervisor can use messages such as:

```text
Navigation FAILED [ABORTED]: Cannot calculate path from start to goal point
Navigation FAILED [REJECTED]: ...
Navigation timeout after 80 s for distance 5.02 m. Last status ACTIVE: Waiting for temporal obstacles to move
```

## Error Sources

Failures can be produced at different points in the request:

```text
location_name is empty
```

Generated by `nav_controller_node` before querying locations.

```text
locations_manager/get: Location '<name>' not found.
locations_manager/get service not available
Timeout/failed calling locations_manager/get
```

Generated before a navigation goal is published.

```text
Navigation FAILED [ABORTED]: ...
Navigation FAILED [REJECTED]: ...
Navigation FAILED [PREEMPTED]: ...
Navigation FAILED [RECALLED]: ...
Navigation FAILED [LOST]: ...
```

Generated after a valid semantic location has been resolved and the navigation
stack publishes a terminal status on `navigation/status`.

These terminal statuses can happen naturally:

```text
ABORTED   planner/controller cannot calculate or execute a path
REJECTED  navigation rejects the goal before execution
PREEMPTED active goal is replaced or cancelled
RECALLED  queued goal is cancelled before execution
LOST      lower-level action state can no longer be tracked
```

## Dynamic Timeout

The navigation request timeout is computed from the current robot pose and goal
pose in the map frame:

```text
timeout = base_timeout_seconds + (distance / expected_speed_mps) * timeout_safety_factor
```

The result is clamped between:

```text
min_timeout_seconds
max_timeout_seconds
```

Default parameters:

```text
map_frame: map
base_frame: base_footprint
base_timeout_seconds: 20
min_timeout_seconds: 45
max_timeout_seconds: 240
expected_speed_mps: 0.25
timeout_safety_factor: 3.0
```

If TF lookup fails, the controller returns failure before publishing a
navigation goal. Without the robot pose, the controller cannot estimate
progress or produce a meaningful timeout. The propagated message looks like:

```text
cannot locate robot TF map -> base_footprint: ...
```

## Timeout Stop Behavior

When the dynamic timeout expires, the controller reports failure and publishes:

```text
topic: /navigation/navigation_ctrl/stop
type: std_msgs/msg/Bool
data: true
```

This stops the base through the `simple_move_node` navigation-control stop
callback.

## Executor Propagation

The service response message is consumed by `navigation_tools::Navigation` via
`GoToDetailed()` and then forwarded by `executor_tools::GoTo`.

That means the final executor action result now carries a useful reason instead
of only a generic navigation failure.

## GoTo Error Test Hook

`nav_controller_node` includes a disabled-by-default test hook so supervisor and
executor tests can exercise terminal navigation statuses without editing
`locations_manager/get`.

Parameters:

```text
enable_test_location_bypass: false
test_location_name: __nav_test__
test_location_x: 0.0
test_location_y: 0.0
test_location_z: 0.0
test_location_publish_goal: true
```

For deterministic terminal-status tests, start the controller with:

```bash
ros2 run nav_controller nav_controller_node --ros-args \
  -p enable_test_location_bypass:=true \
  -p test_location_name:=__nav_test__ \
  -p test_location_publish_goal:=false
```

Then run the supervisor test suite:

```bash
ros2 run supervisor_manager supervisor_goto_test_node --ros-args \
  -p scenario:=nav_controller_error_suite \
  -p terminal_location:=__nav_test__
```

With `test_location_publish_goal=false`, the controller does not send a real
`nav_control/goal` for `__nav_test__`; it only waits for the injected
`navigation/status`. This avoids a natural planner status racing the test
status.
